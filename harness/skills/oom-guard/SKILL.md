# Защита от OOM-killer

Надеваешь шляпу **инфраструктурного ремонтника**. В отличие от `server-audit`
(зеркало) — здесь ты меняешь среду, значит работают гейты: бэкап перед правкой,
`go` владельца на прод, никакого деструктива без отката.

## Главное правило диагностики

> **«Тормозит» — это про память, а не про диск.**

Классическая ошибка: слышишь «сервер тормозит, ничего не запускается» — и
бежишь смотреть `df -h`. Диск при этом обычно свободен. Настоящая причина —
исчерпание RAM: ядро перестаёт работать и начинает выживать, `kswapd0` жжёт
CPU, а `oom-killer` молча расстреливает процессы. Со стороны это выглядит
ровно как «программа не запускается» — она стартует и её убивают за секунды.

**Симптомы, указывающие на OOM:**

- сервис/агент запускается и молча исчезает без сообщения об ошибке;
- `load average` высокий при низком `%CPU` у всех процессов;
- `kswapd0` в топе по накопленному CPU-времени;
- всё «через раз»: то запускается, то нет (зависит от того, хватило ли памяти
  именно в этот момент).

## Шаг 0 — диагностика (read-only, без go)

```bash
free -h                      # available и SWAP — главные числа
swapon --show                # пусто = swap нет вообще (частая причина)
uptime; nproc                # load average против числа ядер
sudo dmesg -T | grep -iE 'oom-kill|Out of memory' | tail -20
df -h /                      # проверить, но НЕ считать причиной по умолчанию
ps aux --sort=-%mem | head -10
```

Строка вида `Out of memory: Killed process NNN (имя)` — прямая улика,
доказывающая диагноз. Приводи её владельцу дословно: это факт с адресом,
а не догадка.

**Осторожно с двойным счётом.** Процессы контейнеров видны с хоста как
обычные (`uvicorn`, `node`), и их легко посчитать второй раз сверх
`docker stats`. Проверяй принадлежность:

```bash
sudo cat /proc/<PID>/cgroup | grep -o 'docker[-/][0-9a-f]\{12\}'
```

Есть совпадение — процесс контейнерный, отдельной строкой в отчёт не идёт.

## Шаг 1 — swap (фундамент, делать первым)

Без swap любой пик = мгновенный расстрел процесса. Размер: **равен RAM**
(при RAM ≤ 4 ГБ) или **половина RAM** (при RAM ≥ 8 ГБ).

```bash
sudo fallocate -l 4G /swapfile        # размер по формуле выше
sudo chmod 600 /swapfile              # обязательно: иначе swap читаем всеми
sudo mkswap /swapfile && sudo swapon /swapfile
sudo cp /etc/fstab /etc/fstab.bak-$(date +%Y%m%d)
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
sudo systemctl daemon-reload          # иначе systemd держит старый fstab
```

Проверка: `swapon --show` показывает файл, `free -h` — ненулевой Swap.

## Шаг 2 — earlyoom (убивает мягко и заранее)

Штатный OOM-killer ядра срабатывает слишком поздно и бьёт вслепую — в жертвы
попадают `systemd` и `dbus` пользовательских сессий, то есть система ломает
сама себя. `earlyoom` вмешивается раньше и выбирает самого прожорливого.

```bash
sudo apt-get install -y earlyoom
```

**Ловушка, стоившая часа отладки.** Аргументы **нельзя** задавать в
`/etc/default/earlyoom`, если в них есть regexp в одинарных кавычках: systemd
передаёт кавычки дословно, `--avoid` молча не применяется, а в логе — дефолтные
пороги. Всегда задавай через drop-in:

```bash
sudo mkdir -p /etc/systemd/system/earlyoom.service.d
sudo tee /etc/systemd/system/earlyoom.service.d/override.conf >/dev/null <<'EOF'
[Service]
ExecStart=
ExecStart=/usr/bin/earlyoom -m 12,5 -s 15,5 -r 3600 --avoid ^(sshd|systemd|systemd-.+|dockerd|containerd|postgres|init|dbus-daemon|sudo)$
EOF
sudo systemctl daemon-reload && sudo systemctl restart earlyoom
```

Пороги: `-m 12,5` = SIGTERM при available RAM ≤12%, SIGKILL при ≤5%;
`-s 15,5` — то же для свободного swap. На тесной машине (RAM ≤ 4 ГБ) бери
12/15; на просторной (RAM ≥ 8 ГБ) хватит 8/10.

`--avoid` защищает то, потеря чего = потеря доступа или данных. **`sshd` в
этом списке обязателен всегда.**

**Проверка обязательна — конфиг мог не примениться:**

```bash
ps -eo args | grep earlyoo[m]                 # видны ЛИ твои аргументы
sudo journalctl -u earlyoom -n 10 --no-pager  # "Will avoid killing... regex"
```

Если в `ps` аргументов нет — drop-in не подхватился, чини, не иди дальше.

## Шаг 3 — защитить sshd от ядра

Последняя линия: если earlyoom откажет, ядро не должно выбрать твой доступ
к серверу.

```bash
sudo mkdir -p /etc/systemd/system/ssh.service.d
sudo tee /etc/systemd/system/ssh.service.d/oom-protect.conf >/dev/null <<'EOF'
[Service]
OOMScoreAdjust=-900
EOF
sudo systemctl daemon-reload && sudo systemctl restart ssh
```

> Перезапуск `ssh` **не рвёт** уже открытые сессии — рвётся только приём новых
> на время рестарта. Но проверь `systemctl is-active ssh` сразу же: если демон
> не поднялся, а ты закроешь сессию — машина потеряна до консоли провайдера.

## Шаг 4 — лимиты памяти контейнерам (требует go: это прод)

Контейнер без `mem_limit` при утечке съедает всю машину. Проверка:

```bash
docker ps -q | xargs docker inspect --format '{{.Name}} {{.HostConfig.Memory}}'
```

`0` = лимита нет.

**Лимит считай по реальному пику, не по текущему снимку** — иначе задушишь
сервис на первом же всплеске:

```bash
id=$(docker inspect --format '{{.Id}}' <контейнер>)
sudo cat /sys/fs/cgroup/system.slice/docker-$id.scope/memory.peak
```

Правило: **лимит ≈ двукратный пик**, округлённый вверх до 64/128/192/256/384/640 МБ.
БД (postgres) — с дополнительным запасом, ей нужны буферы.

В compose:

```yaml
  сервис:
    mem_limit: 384m
```

Сумма лимитов **может превышать** RAM — это потолки, а не резервирование.
Их задача — не дать одному сервису утечь во всю машину.

Применение:

```bash
cp docker-compose.yml docker-compose.yml.bak-$(date +%Y%m%d-%H%M%S)
docker compose config              # валидация ДО применения
docker compose up -d --no-build    # НИКОГДА не down: роняет БД
```

`--no-build` защищает от незапланированной пересборки образов.

**Проверка, что лимит не душит:**

```bash
sudo cat /sys/fs/cgroup/system.slice/docker-$id.scope/memory.events | grep -E '^(oom|max) '
```

`max 0 oom 0` — сервис ни разу не упёрся в потолок. Ненулевые значения =
лимит занижен, поднимай.

## Шаг 5 — убрать накопители мусора

Типовой накопитель на машине с VS Code Remote: версии сервера в
`~/.vscode-server/cli/servers/` не удаляются сами и копят **по ~500 МБ RAM
и ~650 МБ диска каждая**. Три версии = гигабайт памяти впустую.

Лечится ежедневным `systemd`-таймером, который сносит версии старше 3 дней
без живых процессов (текущую из `lru.json` — не трогать). Причина накопления
обычно на стороне клиента: настройка VS Code
`remote.SSH.serverShutdownTimeout` (минуты, дефолт 60) выставлена в огромное
значение — **правится у владельца на его машине, не на сервере**, скажи ему.

Прочие: `docker builder prune -af` (кэш сборки легко копит гигабайты),
`docker image prune -f`. **`docker volume prune` — не запускать**: в томах
живут данные БД.

## Шаг 6 — финальная проверка и отчёт

```bash
free -h; uptime                      # available вырос, load упал
systemctl is-active earlyoom ssh
docker ps                            # все контейнеры Up
```

Плюс проверь сервисы снаружи (`curl` по доменам) — рестарт мог что-то не
поднять. Отчёт владельцу: было → стало числами, что осталось незакрытым.

## Границы скилла

- **Прод** (рестарт контейнеров, правка compose) — только по явному `go`.
- **Бэкап перед каждой правкой** конфига (`fstab`, `docker-compose.yml`).
  Все изменения — через drop-in, откат = удаление одного файла.
- **Не глуши сервисы владельца** ради освобождения памяти, не спросив: то,
  что выглядит лишним процессом, может быть его рабочей сессией.
- **Настройки не создают память.** Они убирают падения. Если машина
  хронически тесная (RAM ≤ 4 ГБ под десяток контейнеров) — честно скажи
  владельцу, что нужен апгрейд железа, а не ещё один тюнинг.

---

*Память — не диск: её не видно, пока она есть. Моя работа — чтобы её
исчезновение не убивало то, что владелец не разрешал убивать.*
