# Параллельное документирование — документ растёт вместе с работой

> Когда эпик/BUG требует фиксации каждого шага (рекон → гипотеза → фикс → проверка)
> до перехода к следующему. Применяется ко всем EPIC и BUG — это способ работы,
> а не исключение. Предотвращает «resolve по памяти» и потерю контекста.

**Домен:** метод
**Автор:** Восьменог
**Дата:** 2026-07-30
**Связанный эпик:** EPIC-009 (Документ-первый)

---

## Контекст

Любая работа — рекон, фикс бага, реализация фичи — состоит из шагов. Без
параллельного документирования каждый шаг живёт только в оперативной памяти
агента: «я помню, что там было, зачем менял и что проверил». Эта память
сбрасывается при смене контекста, перезагрузке сессии или при переходе
к следующему шагу. Resolve превращается в «вспомни, что делал».

Этот tech-doc — не про «как заполнять шаблон», а про **ритм работы**:
рекон → записал → гипотеза → записал → фикс → записал → проверка → записал.
Шаг без записи — потерянный шаг.

---

## Проблема

**Без параллельного документирования:**

- Resolve эпика пишется постфактум, по памяти — теряются детали, причины
  решений, отвергнутые гипотезы
- При эскалации Минотавру контекст пересказывается словами вместо ссылки
  на документ — теряется точность
- После неудачной гипотезы нет записи «я это уже пробовал» — можно пойти
  по тому же кругу
- resolve занимает заметно больше времени, чем если бы запись велась по ходу

---

## Решение

### Четыре обязательных чекпойнта

Каждый шаг работы фиксируется в документе **до** перехода к следующему:

1. **Рекон** → записано: что прочитано/получено, какие данные, структура
2. **Гипотеза / причина** → записано: предполагаемая причина проблемы,
   какие альтернативы рассматривались (если есть)
3. **Фикс** → записано: что изменено, какие файлы, почему именно так
4. **Проверка** → записано: что проверено, каким способом, результат

> Если шаг не потребовал записи (гипотеза очевидна и единственна) —
> напиши «нет» с обоснованием. Не удаляй чекпойнт.

### Куда писать

- **В EPIC** — в секцию «Ход работы» (таблица Дата-Событие-Результат)
- **В TASK** — в секцию «Ход работы» (таблица Шаг-Что сделано-Результат)
- **В BUG** — в секции «Причина», «Фикс», «Верификация» и таблицу
  «Ход работы»

### Как это выглядит на практике

Плохо:
```
1. Прочитал код компонента
2. Понял, в чём проблема
3. Починил
4. [через час при resolve] «ну, я там пофиксил overflow, вроде работает»
```

Хорошо:
```
1. Рекон: файл/X.ts:42 — overflow: hidden на родителе. grep по всем
   обработчикам клика. Структура: Dropdown → LessonList → ScrollWrapper.
2. Гипотеза: ScrollWrapper.closest('.modal') блокирует
   event.stopPropagation(). Альтернатива: может быть CSS.
3. Фикс: ScrollWrapper.ts:15 — убрал stopPropagation, заменил на
   e.preventDefault(). Почему: stopPropagation не давал закрываться
   по клику вне.
4. Проверка: клик вне — закрывается. Клик внутри — не закрывается.
   ScrollWrapper не сломался (скролл работает).
```

## Антипаттерны

- ❌ **Сделал → вспомнил при resolve** — самый частый. Resolve по памяти
  теряет 30-50% деталей. Цена: потерянные гипотезы, повторные итерации.
- ❌ **«Я помню, зачем менял»** — не помнишь. Даже через час. Запиши сразу.
- ❌ **Документ создан после фикса** — классика BUG-019-003. Баг пофикшен,
  документ создан постфактум. Потеряна первая гипотеза (которая не сработала,
  но могла быть правильной при другом контексте).
- ❌ **«Потом оформлю»** — не оформишь. Или оформишь, но хуже.
- ❌ **Пустая таблица хода работы** — хуже, чем отсутствие. Создаёт иллюзию,
  что работа документирована. Если шаг не потребовал записи — напиши «нет».
