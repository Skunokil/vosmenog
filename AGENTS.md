```
  vosmenog/           # ВОСЬМЕНОГ: персона и продукт для opencode

```

**Граница слоёв (EPIC-026 Ф4):** `harness/` не знает про `vosmenog/` — ни файлов, ни путей
(проверка: `./check-boundary.sh` из корня репо). `vosmenog/` пользуется харнессом через установленные
пути `~/agent-os`. Установка на диске от разбиения не зависит: `~/agent-os`, `~/.config/opencode`,
`~/.local/bin` выглядят одинаково.

> **Инфраструктурный проект:** работы вне продуктовых проектов (бэкап, ssh, git,
> обновления) живут в `~/projects/infra` + `team-work/infra/`. Развёртывание —
> скилл `infra-bootstrap` (см. `harness/skills/`), статус при старте — проверка
> в STARTUP.md. Подробно: `METHOD.md` → раздел «Инфраструктурный проект (infra)».

## Документ-первый (протокол)

**Любой вход → классификация → документ → работа с обновлением.**

| Этап | Действие |
|------|----------|
| Вход | Классифицировать запрос: фаза (EPIC), баг (BUG), штурм (backlog) |
| До действия | Создать/открыть документ. Без документа — только вопрос на уточнение |
| Рекон → запись | Что прочитано, какие данные |
| Гипотеза → запись | Предполагаемая причина, альтернативы |
| Фикс → запись | Что изменено, где, почему |
| Проверка → запись | Результат (сработало / нет) |

Подробно: `METHOD.md` (правило 0, чекпойнты).

## Как улучшать агента

- Улучшение агента = правка **дистрибутива** (`harness/` или `vosmenog/` в этом репозитории).
  Живые файлы на сервере (`~/agent-os/`, `~/.config/opencode/`) — результат
  раскатки, правятся через дистрибутив.
- **Три уровня:** GitHub-репо (источник) → `~/agent-os` (клон репо, дистрибутив
  на сервере) → `~/.config/opencode/` (живой конфиг, откуда работает агент).
- **Порядок изменений:** (1) правка в `harness/` или `vosmenog/` клона репо → (2) коммит + push
  в GitHub → (3) накатка: `vosya-update` (запускает `update.sh` из вашего клона; `~/agent-os` — установка из копий, не клон, `git pull` там не делается)
- **Любое обновление дистрибутива сопровождается сообщением для людей** (решение владельца 2026-10-12): до пуша — новая запись сверху в
  `CHANGELOG.md` простыми словами (что даёт, нужно ли что-то делать, как откатить, что вручную, что автоматически) и обновлённый раздел
  «Последние обновления» в `README.md`. Хеши коммитов и номера эпиков — язык разработчика, пользователю они ничего не говорят. `update.sh` печатает
  верхнюю запись после обновления, а проверка обновлений на старте сессии пересказывает её агенту; нет записи — пересказывать нечего.
- Править файлы прямо в `~/agent-os` в обход git можно, но правки потеряются
  при следующем pull.
- Навыки/скиллы — улучшаются по итогам ретро в процессе работы, обычным циклом.

## Границы репозитория

- **В репозиторий** — только обезличенный метод работы: METHOD.md, шаблоны,
  AGENTS.md, setup/update скрипты. Никаких серверных конфигов, секретов,
  проектной специфики конкретной установки.
- **Вне репозитория** — серверные конфиги (CLAUDE.md, opencode.json, .bashrc),
  STARTUP.md, team-work/ документы. Они живут на сервере, правятся отдельно.
- **Общие практики** — выносятся в репозиторий (METHOD.md).
- **Локальные процедуры** — остаются в team-work/ и серверных конфигах.

## Память смены — три горизонта

Порядок чтения при старте задан методом (`STARTUP.md` → «Старт сессии»):

| Горизонт | Файл | Как читается |
|---|---|---|
| Горячий | `~/projects/team-work/vosmenog/sessions/next-session.md` | всегда, целиком |
| Тёплый | эпик или задача текущей фазы | по ссылке из горячего |
| Холодный | `~/projects/team-work/vosmenog/sessions/journal.md`, `archive/` | **никогда целиком — грепом по адресу** |

Пороги (в знаках, `wc -m`): строка журнала ≤ 200, `journal.md` ≤ 15 000,
`next-session.md` ≤ 4 000. Горячий файл **перезаписывается** в конце смены.

## Практики сервера — не здесь

Канал с владельцем, несколько сессий, общее дерево, границы прода — практики
конкретной машины, а не метода. Они живут в карте сервера установки
(на этой машине — `~/projects/team-work/SERVER.md`) и подгружаются в обе среды
сами (EPIC-026). В дистрибутив их не возвращаем.
