# Person Maker v2 — лор, навыки, переключение

## Назначение

Создавать переносимого ИИ-напарника, не смешивая литературного персонажа, процессную роль, доступные навыки и права конкретного runtime. Вход — явный запрос на новую персону, доработку действующей или переключение. Используй Core и Project Adapter как ограничения.

## Правила

- Не задавай длинный брифинг. Один существенный вопрос за раз, известное не переспрашивать. Первым делом определить, зачем нужна новая персона и какое поведение можно проверить.
- Открыть/продолжить один Session Record до классификации work. Изначально classification=undecided. Отсутствие файла в чате означает prepared / not_saved, а не «сохранено».
- Никаких лоров, основанных на реальных людях или чувствительных материалах без разрешения. Публичность создаваемого пакета — отдельный осознанный выбор владельца, по умолчанию private.
- Если есть отдельный редактор/шоураннер, можно предложить передачу ему лора; без доступного и разрешённого инструмента нельзя заявлять, что другой агент участвовал.
- Не менять Core, project instructions, роли, права и GO; подключение навыка не означает право использовать инструмент.
- Навык может описывать сценарий без bash, файловой системы, hook и native Skill API. Не выдавать симуляцию за реальное действие.

## Последовательность

### 1. Work Contract

Зафиксировать назначение, пользователя, ожидаемое отличие от текущего помощника и 1–2 наблюдаемых критерия проверки. Установить среду (чат, проект, CLI), какие источники доступны и где владельцу допустимо сохранять пакет. Известный канон сначала прочитать; не создавать дубли.

### 2. Лор и характер

Разработать вместе с владельцем: роль в истории, культурные отсылки и двойное дно имени (не обязательно), происхождение, ценности, внутренний конфликт (только если помогает характеру), характер речи, юмор, запреты, отношения с пользователем, кинестетику (если нужна).

Выдать отдельно:
- **persona** — короткие исполняемые инструкции поведения;
- **lore** — подробный мир, объяснения отсылок и история решений, не обязательные для каждой реплики.

Предложить варианты там, где нет решения; выбранный вариант становится каноном только после согласия владельца. Лор не должен диктовать ложные факты о возможностях ИИ.

### 3. Набор навыков

Составить 2–5 типовых задач персоны. Для каждой указать существующий skill с адресом или потребность создать новый; триггер, вход/выход, критерий проверки, реальные зависимости. Учитывать совместимость среды. Не переименовывать reference-файл в «установленный» skill.

### 4. Упаковка

Подготовить pack.json по ../agent-packs/PACK_CONTRACT.md: persona_sources, lore_sources, skills и visibility. Источник истины один; манифест — ссылки, не зеркальная копия исходников. Добавить небольшой адаптер среды, только если он действительно нужен. Готовые документы и установки не смешивать.

### 5. Активация или переключение

Проверить, доступен ли выбранный pack и реально ли прочитаны инструкции. При логическом переключении в том же чате сохранить Session Record и проектные правила; объявить, что меняется только голос и приёмы работы, а не отдельный исполнитель. При передаче независимому агенту использовать отдельный handoff.

### 6. Испытания

Провести: (a) типовую работу по заявленному skill; (b) проверку узнаваемости голоса; (c) негативный тест доступа/GO; (d) выбор другого доступного профиля и возврат; (e) восстановление Session Record в новой сессии; (f) тест недоступного/неустановленного источника. Для каждого записать expected, observed, evidence_ref и класс подтверждения.

### 7. Приёмка и поддержка

Сверить поведение с исходной целью. Попросить утвердить лор, набор навыков и область публикации только там, где решение ещё не дано. Без отдельного GO не менять настройки, Git, проект, сервер или доступы. При успешной установке и независимой проверке обновить статус; иначе оставь prepared / not_installed / not_verified.

## Проблемы и восстановление

- Не найден source → не сочинять персонажа; указать source_unverified, запросить один точный источник.
- Характер нарушает строгие правила проекта → приоритет у правил проекта; исправить только пакет, не ослаблять стопы.
- Редактор или субагент недоступен → предложить ручной handoff, не заявлять о делегировании.
- Голос поменялся, а навыки не работают → проверить наличие инструкций и фактических инструментов, не обещать магию.
- Параллельные копии лора разошлись → выбрать канонический источник с владельцем; не сливать молча.

**Результат:** один подготовленный пакет с явным контуром публикации, проверенными ссылками, прозрачным статусом установки и записью передачи.
