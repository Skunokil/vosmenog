# ONBOARDING.md — Фреймворк работы с Восей (Vosmenog)

Человеко-док. **Для владельца, не для агента** — агент его не грузит.
Здесь «почему» и «как ты ведёшь процесс»; короткий императив для агента — в `METHOD.md`.

---

## 1. Три слоя

| Слой | Где живёт | Меняется при |
|------|-----------|--------------|
| Ядро метода + профиль | `~/agent-os/METHOD.md` | смене модели/метода |
| Режим-исполнитель (права) | `~/.config/opencode/agents/Vosmenog.md` | смене политики доступа |
| Слоты проекта | `<проект>/AGENTS.md` | новом проекте/стеке |
| Память | `~/.config/opencode/memory/` | каждой сессии |
| Панель доверия (TUI) | `~/.config/opencode/tui.json` + `plugins/trust-panel.tsx` | обновлении дистрибутива |

Граница: в ядро — принцип, в слот — команда, которая его реализует.

## 2. Как opencode грузит контекст (v1.17)

- **instructions[]** (`~/.config/opencode/opencode.json`) → `STARTUP.md` + `METHOD.md`,
  всегда, во всех режимах (build/plan/Vosmenog).
- **авто по дереву cwd** → `<проект>/AGENTS.md` (слоты) — когда агент в папке
  проекта; глобальные правила — `~/.config/opencode/AGENTS.md`.
  `AGENTS.md` — родной формат opencode; `CLAUDE.md` подхватывается только как
  fallback (первый совпавший в категории побеждает — если положить оба, `CLAUDE.md`
  молча проиграет). Поэтому везде используем `AGENTS.md`.
- **agents/** → субагенты-режимы (Vosmenog), переключаются табом.

## 3. Два режима — твой выбор за рулём

- **build / plan** (встроенные) — твоя свобода, когда сам ведёшь и быстро.
- **Vosmenog** (наш) — строгий режим: урезанные права (bash под ask, прод недостижим,
  edit с подтверждением), обязан документировать эпик, эскалировать развилки.
  Переключаешь **табом**. Дисциплина включается осознанно.

## 4. Команда: роли гибкие

Работа всегда командная — минимум двое. Распределение ролей — **рекомендуемое
для старта**, не жёсткое. Со временем роли могут меняться.

### Рекомендуемое распределение

- **Эпир (владелец)** — воля, цель, ответственность, финальный суд. Замышляешь,
  решаешь развилки, держишь go-гейт и один касаешься прода. Бестии сильнее тебя
  в навыках — но не в ответственности.
- **Минотавр (голова в облаке)** — внешний облачный мыслитель (веб-Клод в проектном
  пространстве). Архитектура, развилки, код, тест-планы, ревью, подготовка ТЗ и PBR.
  Умнее агента, но рук на сервере нет — действует через тебя и артефакты.
- **Восьменог (руки)** — агент на сервере: рекон, реализация по ТЗ, документооборот,
  ведение team-work, resolve.

### Гибкость

Эти роли — **шаблон**, не приговор. Конкретный проект может потребовать иного
распределения. Ключевое不变ое:
- **Прод** — только владелец (один касается боевого стека).
- **Архитектура/развилки** — решает владелец (Минотавр готовит варианты, владелец судит).
- **Рекон/реализация/resolve** — исполнитель.

## 5. Два формата работы

Фреймворк гибкий: команда от двух до трёх, в зависимости от сложности.

| Формат | Кто за столом | Когда |
|--------|---------------|-------|
| **Пара** | Эпир + Восьменог | Старт, простые задачи, известные паттерны |
| **Тройка** | Эпир + Восьменог + Минотавр | Зона неопределённости, архитектурные развилки, PBR |

**Пара — дефолт.** Достаточна для большинства задач. Вося работает по ТЗ,
эпикархитектуру решаешь ты. Минотавра нет — exchange-папки дремлют, ничего не ломается.

**Тройка — когда выросла сложность.** Критерии перехода:
- Задача требует архитектурного решения до кода (выбор стека, паттерна, схемы данных)
- Нужен PBR перед go (внешний взгляд на контракт эпика)
- Несколько параллельных эпиков с пересечениями
- Проект в фазе роста, где ошибки архитектуры дороже исправлений

**Как добавить Минотавра** (GUIDE, шаг 10):
1. Создай проектное пространство в Claude Projects
2. Загрузи файлы головы из `~/agent-os/payload/shared/skills/`
3. Скажи: «Ты — Минотавр. Читай session_start.md»

**Не бойся начинать с пары.** Минотавр — надстройка, а не порог входа. Простые задачи
не нуждаются в трёх за столом. Добавишь голову, когда почувствуешь: «тут нужен
внешний взгляд».

## 6. Цикл работы через Vosmenog

1. **Обсуждение** — вы вместе разбираете задачу, ты решаешь развилки.
2. **Агент пишет EPIC** — формализует итог (DoR/DoD/AC/Decisions). Не выдумывает —
   записывает принятое. Незакрытая развилка = пустая ячейка = эпик не готов.
3. **PBR** — выносишь эпик на PBR (Минотавр / внешний ревью-канал) на ревью контракта.
4. **go → дробление на TASK** — атомарные, по адресам `файл:строка`.
5. **Баги** по ходу → отдельный тип **BUG**, привязка к эпику.
6. **Resolve** — агент пишет хвостом эпика: что/почему, сверка с vision/стеком.

## 7. Когда EPIC, а когда сразу TASK/BUG

- **EPIC** — фаза с несколькими задачами, новая фича, архитектурный сдвиг.
- **Сразу TASK** (без эпика) — одиночное изолированное изменение по понятному адресу.
- **Сразу BUG** — точечный фикс. Если повлиял на решения — отрази в эпике-родителе.

Не плоди EPIC ради однострочника — это церемония вхолостую.

## 8. Эскалация: когда агент зовёт Минотавра

Агент рекомендует вынести вопрос Минотавру, когда:
эпик оформлен (PBR) · архитектурная развилка · нетривиальный коммит (code review) ·
resolve разошёлся с планом · два провала подряд. Это не слабость агента — это
дешёвая страховка вместо дорогой ошибки.

## 9. Профиль исполнителя (GLM): как писать ТЗ

- адресуй `файл:строка`, не «найди место»;
- развилки разжёваны в EPIC — агент не достроит архитектуру;
- атомарные шаги, каждый с критерием верификации;
- форсь Max effort на сложном;
- вывод ≤128K — не требуй простыней.

Этот исполнитель при нехватке ТЗ **заполняет вакуум генерацией, а не вопросом** —
поэтому голую цель он обязан отбить стопом, а ты обязан дать оформленный эпик/таск.

## 10. Периметр (барьер, не увещевание)

Vosmenog физически не дотянется до боевого/общего стека и не запушит — это в его
правах (`Vosmenog.md` → `external_directory`), не в просьбах. Конкретные каталоги
прода/секретов объявляются **при установке** (GUIDE, шаг «периметр») и в слотах
проекта — только владелец знает, что у него прод. Если проекту нужен свой
бэкенд/деплой — агент поднимает его в СВОЁМ периметре проекта, не на общем стеке.
Касание общего прода — только ты.

## 11. Уровни доверия — как это работает

Ось доверия — единый регулятор: сколько агент останавливается и объясняет.
Уровень живёт в `~/.config/opencode/memory/user-profile.md`, переключается вживую
**панелью в TUI** (`alt+1/2/3`, `alt+t` — свернуть/развернуть; цвета:
1=зелёный, 2=жёлтый, 3=красный).

**Три пресета:**

| Уровень | Частота остановок |
|---------|-------------------|
| 1 — обучающий | объясняет каждую команду до ввода; согласует всё, включая чтение |
| 2 — средний | рекон/чтение свободно; каждая изменяющая команда согласуется |
| 3 — продвинутый | согласуется только принципиальное (бэкап/откат) |

**Границы оси.** Доверие крутит *разговорчивость*, не права. На всех уровнях
стоят: периметр (`external_directory`), три стопа, `git push` под подтверждением.

**Правило `min`.** Уровень = минимум (строже) из профиля пользователя и
опционального слота `AGENTS.md` проекта. Проект может только **ужесточить**,
не ослабить. Нет слота — берётся профиль.

**Что профиль НЕ трогает.** Три стопа, рекон и ядро метода — без права отмены
профилем. Отмена — только правкой METHOD в git (осознанная переоснастка, не настройка).

## 12. Веб-доступ (рекон по интернету)

Агент умеет загружать конкретные URL (`webfetch`) — читает документацию, примеры,
API и отвечает по содержимому со ссылкой на источник. Это сняло ограничение
«рекон по памяти»: если нужно понять внешний инструмент, Вося читает его доки вживую.

- **Есть:** webfetch (конкретные URL). Разрешён в дистрибутиве
  (`~/.config/opencode/agents/Vosmenog.md`).
- **Нет:** websearch — поиск по интернету вне комплекта, провайдер отдельной
  инфраструктуры (на момент раскатки падал с 403).

Пользователь: если агенту нужен источник — дай URL руками. Агент сам не ходит
в веб «просто посмотреть».

## 13. Журналирование

- Агент ведёт journal/archive по `STARTUP.md` в конце своей сессии.
- Сессии «ты + Минотавр» (без агента) — journalируй вручную, иначе теряются.
- Resolve эпиков — в `team-work/<project>/epics/` (операционка); утверждённые
  продуктовые/техдоки — в `docs/` (durable). Индексная строка — в journal.
