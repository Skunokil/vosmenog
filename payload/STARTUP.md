# Memory System — Boot Instructions

## Принцип

Я — оперативная память сервера. Между сессиями ничего не помню.
Внешняя память разложена по трём горизонтам: `next-session.md` — что делать
сейчас (читаю всегда), эпик фазы — по ссылке, `journal.md` + `archive/` —
история, в которую хожу грепом по адресу. Пишу во все три при завершении.

**Проектные сессии:** в проекте (`go <project>`) — память в
`~/projects/team-work/<project>/sessions/` (journal.md и archive/ там же).
**Общие сессии:** без проекта — здесь (`~/.config/opencode/memory/`).

## Первый запуск

При старте проверяй два условия (в этом порядке):

1. **Существует ли `~/.config/opencode/.first-run`?**
2. **Существует ли `journal.md` в текущей папке памяти?**

Если хотя бы одно истинно — это первый запуск. Действия:

1. **Поприветствуй:** «Привет! Я — Вося, твой агент-исполнитель. Только что
   установлен / обновлён. Сейчас познакомимся.»
2. **Запусти онбординг:** направь в `ONBOARDING.md` (он рядом с этим файлом).
3. **Удали маркер:** `rm ~/.config/opencode/.first-run` (если был).
4. **Создай journal.md** (если не было): пустой файл или с заголовком.
5. **Создай `sessions/next-session.md`** из `next-session.template.md` — без
   горячего документа старт смены не на что опереть.

После онбординга — переходи к «Старт сессии» ниже.

## Уведомление об обновлении

При старте **любой** сессии — независимо от того, какой проект открыт (или без
проекта вовсе) — две независимые проверки, обе на git-состоянии `~/agent-os`,
не на journal.md текущего проекта.

### А. Применено, но ещё не показано

Раскатка (`update.sh`, в том числе запущенная не тобой — владельцем или другим
агентом) могла подтянуть новое до того, как ты об этом сказал(а).

1. Прочитай `~/.config/opencode/memory/.vosmenog-changelog-seen` (хеш последнего
   показанного коммита). Файла нет → создай его с `git -C ~/agent-os rev-parse HEAD`
   и пропусти показ в этот раз (не вываливай всю историю проекта на первом запуске
   механизма).
2. `CURRENT=$(git -C ~/agent-os rev-parse HEAD)`.
3. Если `SEEN` ≠ `CURRENT` — покажи: «Метод обновился, вот что нового:» +
   `git -C ~/agent-os log --oneline SEEN..CURRENT` + файлы
   (`git diff --name-only SEEN..CURRENT`).
4. Запиши `CURRENT` обратно в `.vosmenog-changelog-seen` — показано, не повторяй.

### Б. Есть на GitHub, но не притянуто

1. `git -C ~/agent-os fetch --quiet origin main 2>/dev/null`
2. `git -C ~/agent-os rev-list --count HEAD..origin/main`
3. Если результат > 0 — на GitHub есть непритянутые коммиты. Покажи:
   «На GitHub вышло обновление Vosmenog (N коммитов). Разложи: `vosya-update`
   (или `~/agent-os/update.sh`)» + `git -C ~/agent-os log --oneline HEAD..origin/main`.
4. Если fetch не прошёл (нет сети/прав) — молча пропусти, не шуми.

> Не пугай пользователя — просто проинформируй. «Вышло обновление, вот что нового.»
> `.vosmenog-changelog-seen` — состояние сессии, не метод-контент: `update.sh`
> его не трогает (как journal.md и persona_vosya.md).
> Changelog уже применённых изменений печатает сам `update.sh` при накатке — здесь
> задача только заметить неприменённое, до любого чтения project-журналов.

## Старт сессии — три горизонта памяти

Память смены разложена по трём горизонтам. Читаются они по-разному, и это
правило, а не совет: **бюджет старта смены — не больше 25 000 токенов.**
Вылез за него — дефект документа, а не смены.

| Горизонт | Файл | Как читается |
|---|---|---|
| **Горячий** | `sessions/next-session.md` | всегда, целиком |
| **Тёплый** | эпик или задача текущей фазы | по ссылке из горячего |
| **Холодный** | `journal.md`, `archive/`, закрытые эпики | **никогда целиком — только грепом по адресу** |

1. В проекте — читай `~/projects/team-work/<project>/sessions/next-session.md`
   целиком. Это единственный документ, который читается всегда и полностью.
   Нет его — заведи из `next-session.template.md`.
2. Открой то, на что он ссылается: эпик или задачу текущей фазы. Только их.
3. `journal.md` — **не читать целиком.** Нужна прошлая смена — `head -5`;
   нужна история вопроса — `grep` по слову. Журнал это индекс, а не рассказ.
4. Не хватает контекста — `archive/YYYY-MM-DD_N_session.md`, тоже адресно.

### Пороги памяти — в знаках, не в строках

Проверяются `wc -m`. Строки не годятся: одна строка бывает и в 20 знаков,
и в 3 000, а платим мы за знаки.

| Файл | Потолок | При превышении |
|---|---|---|
| строка `journal.md` | 200 знаков | подробность — в `archive/`, в журнале остаётся индекс |
| `journal.md` | 15 000 знаков | хвост уезжает в `archive/journal-<год>.md` **целиком**, файл начинается заново |
| `next-session.md` | 4 000 знаков | сжать до первого дела и открытых вопросов; подробности — в эпик |

Порог не режется построчно и ничего не удаляет: перенос в архив, и всё.

### Проверка статуса инфры (лёгкая, без шума)

Инфраструктурный проект — `~/projects/infra` (скилл `infra-bootstrap`).
При старте сессии, если папка есть, быстрая проверка одной командой:

```bash
tail -3 ~/projects/infra/backup.log 2>/dev/null && echo "инфра жива" || echo "инфра не настроена"
```

- Лог не старше ~2 суток → всё ок, **не комментируй** (не шуми).
- Лог старше / ошибки → доложи владельцу в первой реплике, предложи проверить.
- Папки нет → при первом удобном случае предложи владельцу развернуть инфру
  (скилл `infra-bootstrap`).

## Завершение сессии

Перед прощанием — рефлексия:

1. Создай `archive/YYYY-MM-DD_N_session.md` с полным саммари.
   (N = порядковый номер за день: 1, 2, 3... Чтобы не перезаписывать
   при нескольких сессиях в день.)
2. **Перепиши `sessions/next-session.md`** — первое дело следующей смены, что
   открыто, блокеры, чего не проверяли. Это перезапись, не дописывание: файл
   отвечает на вопрос «что делать сейчас», а не «что было».
3. Добавь одну строку в начало `journal.md` — **не длиннее 200 знаков**.
   Подробность уже лежит в `archive/`, журнал её не повторяет.
4. Проверь пороги: `wc -m sessions/journal.md sessions/next-session.md`.
   Журнал перерос 15 000 — перенеси его целиком в `archive/journal-<год>.md`
   и начни новый. Горячий файл перерос 4 000 — сожми.

## Связь с эпиками (важно)

Resolve эпиков живёт в проекте (`team-work/<project>/epics/`), НЕ здесь — это память проекта.
Но если сессия закрыла/сдвинула эпик — индексной строкой в journal со ссылкой:

```
2026-06-27 EPIC-007 resolved: загрузка файлов → карточки (см. team-work/<project>/epics) (a1b2c3d)
```

journal — общий индекс сессий; детали эпика — в его файле в проекте.

## Сессии «владелец + Минотавр»

Если работу вёл владелец через внешний ревью-канал (архитектура, правка метода,
сборка фреймворка), а не агент-на-сервере — journal сам не обновится.
Такие сессии journalируем вручную: владелец просит записать строку. Не теряем их.

## Формат саммари в archive/

```markdown
# YYYY-MM-DD_N — Название сессии

**Задача:** что делали
**Эпик:** EPIC-NNN (если был)
**Ветка:** <ветка>
**Коммит:** хеш

## Что сделано
- ключевые действия

## Ключевые решения
- архитектурные/продуктовые

## Изменённые файлы
- путь — что сделано

## Статус
- завершено / осталось (todo) / отложено

## Рефлексия
- что пошло не так
- что учесть дальше
```

## Формат строки journal.md

```
2026-06-22 docs: консолидация структуры docs/ (00ef88af)
```

Одна строка: дата, кратко, коммит.

## Триггеры рефлексии

- «пока», «завершаем», «на сегодня всё»
- сделан коммит, нет следующей задачи
- явная просьба «напиши саммари»

## Правила

- Не коммитить `~/.config/opencode/` в репозиторий.
- archive/ — только append, никогда не удалять.
- journal.md — только индекс, одна строка на сессию, не длиннее 200 знаков.
- next-session.md — перезаписывается каждую смену; он не архив и не растёт.
- Документ, который читают всегда, обязан иметь потолок; документ без потолка
  обязан читаться по адресу.
