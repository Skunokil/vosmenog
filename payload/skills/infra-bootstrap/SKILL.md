# Развёртывание базовой инфры

Этот скилл — чек-лист и сценарий для работ по базовому окружению сервера.
Ты — тот же Вося: суровый к костылям, но здесь ведёшь по предсказуемому
пути, а не изобретаешь. Правки платформенных файлов — только владелец;
ты исполняешь в периметре `infra`.

## Что такое инфраструктурный проект

Работы, которые не вписываются в продуктовые проекты (бэкап, ssh, git,
обновления, мониторинг) — живут в **`~/projects/infra`** (скрипты) и
**`team-work/infra`** (эпики). Периметр — весь сервер.

Шаблоны проекта — `payload/infra-project/` в дистрибутиве. При установке
агента (`setup.sh`) проект `infra` появляется автоматически с эпиками:
EPIC-001-backup (эталон), черновики SSH/git, обновления.

## Шаг 0 — проверка статуса (сначала прочитай, потом делай)

```bash
ls ~/projects/infra/ 2>/dev/null && echo "инфра-проект есть" || echo "НЕТ инфра-проекта"
tail -3 ~/projects/infra/backup.log 2>/dev/null
ls ~/projects/team-work/infra/epics/ 2>/dev/null
```

Что уже есть — не пересоздавай (идемпотентность). Доложи владельцу
текущий статус и предложи недостающее. Без go — только чтение.

## Шаг 1 — SSH-доступ к GitHub

Цель: `ssh -T git@github.com` отвечает приветствием.

```bash
ssh -o StrictHostKeyChecking=accept-new -T git@github.com
```

Если нет ключа:
1. `ls ~/.ssh/` — есть ли ключ. Нет — сгенерировать (`ssh-keygen -t ed25519`), публичный ключ показать владельцу (`cat ~/.ssh/id_ed25519.pub`) — добавит на GitHub сам (секрет/ключ — его зона).
2. Если ключ есть, но GitHub не узнаёт — владельцу добавить публичный ключ в GitHub → Settings → SSH keys.

> Ключи не копируются в чат приватно. Публичный ключ можно показать — он для этого.

## Шаг 2 — git-репозитории проектов

- Каждый проект (`~/projects/<name>`) инициализирован git, remote на GitHub, ветка `main`.
- Для новых: `git init`, `git branch -m main`, добавить remote (URL даёт владелец), первый коммит, push — владелец подтверждает создание репо на GitHub.
- Секреты — не коммитить: `.env*` в `.gitignore`.

## Шаг 3 — бэкап restic + S3

Разворачивается по шаблонам `payload/infra-project/` (или повторяет EPIC-001-backup в `team-work/infra/epics/`):

1. **`.env`** — креды S3 и пароль restic. Шаблон `.env.example` → `.env` (`chmod 600`), владелец заполняет САМ (nano). Правила: значения в кавычках (спецсимволы `& $ #` ломают `source`), `RESTIC_REPOSITORY=s3:host/bucket` (слэш, не двоеточие). Пароль restic — в менеджер паролей владельца.
2. **Установка restic**: `sudo apt-get install -y restic`.
3. **Инициализация**: `source .env && restic init` → `restic snapshots` (пусто — ок).
4. **Скрипты** (из шаблонов): `backup-db.sh` (pg_dump контейнеров → restic, тег `db`), `backup-files.sh` (файлы + `/etc` через `sudo -n`, тег `files`), `backup.sh` (оркестратор + ротация `restic forget --keep-last 14 --group-by tags --prune`).
5. **Cron**: ежедневно `0 3 * * * backup.sh`, лог в `backup.log`.
6. **Восстановление**: `restore.sh` + `RESTORE.md` (из шаблонов).
7. **Тест восстановления**: реальная заливка дампа во временную тестовую БД, сравнение количества таблиц (не в прод!).

> Правила из EPIC-001-backup: бэкап без теста восстановления — архив мусора;
> перезапись одного объекта — потеря страховки (нужна ротация ≥7);
> секреты не светить в чат/git/логи.

## Шаг 4 — обновления

- `sudo apt-get update && sudo apt-get upgrade` — осознанно, с владельцем.
- Pending kernel upgrade → предложить ребут (`sudo shutdown -r +1`), предупредить об обрыве сессии, проверить после (контейнеры Up, cron жив).
- После ребута — проверка бэкапа и сервисов.

## Шаг 5 — финальная проверка

```bash
restic snapshots            # после source .env — снапшоты есть
docker ps                   # контейнеры Up (restart: unless-stopped)
crontab -l                  # задача бэкапа на месте
tail -5 ~/projects/infra/backup.log
```

Доложи владельцу: что развёрнуто, что осталось (например, «проверка cron 2+ суток → resolve»).

## Правила скилла

- **Секреты** (креды S3, пароль restic, приватные ключи) — заполняет владелец, в чат не пишутся, в git не попадают.
- **Прод/деструктив** (заливка БД на прод, ребут, снос) — только владелец по явному go.
- **Идемпотентность**: что уже настроено — не трогай, только проверь и доложи.
- **Документ-первый**: работы оформляй как EPIC в `team-work/infra/` (шаблон EPIC-001-backup — эталон).
- Если встретил развилку (провайдер S3, имя бакета, состав путей) — эскалируй владельцу, не угадывай.
